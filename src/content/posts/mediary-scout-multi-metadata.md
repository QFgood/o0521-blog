网盘里的影视资源越来越多，管理起来却未必越来越方便：电影、剧集、动漫分散在不同目录，新番要反复检查更新，重新部署服务之后，还可能遇到“文件都在，媒体库记录却没了”的情况。

**巡影 · Mediary Scout 多元数据版**，就是围绕这些日常需求展开的一个开源项目。它通过 Docker 自部署，把作品搜索、资源获取、网盘转存、入库验证和后续追更串联起来，让维护个人媒体库少一些重复操作。

项目地址：[QFgood/mediary-scout-o0521](https://github.com/QFgood/mediary-scout-o0521)

## 从搜索作品，到持续追踪更新

巡影的基本使用方式很直接：搜索想看的作品，发起获取或预定，后台 Agent 再根据配置搜索资源、选择候选、转存到绑定的网盘，并验证是否成功入库。

对于持续更新的剧集和动漫，系统还会通过后续巡检检查播出进度，尝试补齐已经播出但尚未入库的集数。

这样一来，用户可以围绕“我要追踪哪部作品”来管理媒体库，把反复搜索和核对文件的工作交给后台处理。当然，最终能否获取成功，仍取决于资源源、模型、网盘和部署网络的实际可用性。

这个版本基于 [Mediary Scout](https://github.com/fancydirty/mediary-scout) 二次开发，目前独立维护，重点放在 **TMDB / AniList 双元数据、动漫原生获取、网盘媒体库恢复，以及按服务选择代理**。部署方面仅维护 Docker 自部署版本，适合放在 NAS、软路由或服务器上，通过浏览器使用。

## 双元数据，让电影、剧集和动漫各有合适的入口

影视管理离不开元数据：作品名称、年份、集数、播出状态，都会影响搜索结果和后续追踪。

巡影多元数据版提供 TMDB 与 AniList 两种搜索入口。电影和剧集可以使用 TMDB，动漫则可以切换到 AniList，同时浏览当季、热门和待播动漫榜单。

对于追番用户，更实用的变化是 **AniList 原生任务**。

支持的动画条目可以直接发起获取、查看详情、加入媒体库并持续追更，无需先手动配置 TMDB 季度映射。后续巡检也会使用对应的 AniList 条目查询播出进度，保留作品原本的来源身份。

例如，某部动画的续作在 AniList 中是独立条目，就可以围绕这个条目进行追踪，减少人工处理不同平台季度划分的工作。动画电影也支持原生获取和未上映预定。

不过，动漫集号本身仍有复杂情况。目前不会自动处理跨季聚合或连续总集号偏移；对于缺乏可靠播出信息的条目，也会保留未知状态，等待进一步确认。

### 中文搜番，也多一层辅助

AniList 的中文译名覆盖并不完整，直接输入中文，有时找不到想要的作品。

项目加入了中文名称辅助搜索：当中文查询没有直接结果时，会尝试通过 TMDB 查找作品原名，再用原名搜索 AniList；对于已经命中的条目，也能利用原名补充搜索续作和特别篇。

这一功能依赖元数据实际收录的名称。遇到中文简称无法命中的情况，仍可以尝试完整译名、日文、英文或罗马字名称。

## 网盘文件还在，媒体库记录可以尝试找回来

另一个很贴近自部署场景的功能，是**从网盘恢复媒体库**。

重新部署或重建数据库后，只要重新绑定原网盘和分类目录，就可以在媒体库中点击「同步网盘资源」，扫描已绑定的 Movies、TV、Anime 目录，尝试恢复作品、季度和已入库集号。

恢复时，系统优先根据目录中的 TMDB / AniList 标识定位作品。对于旧的“片名（年份）”目录，则需要片名、年份和类型能够唯一匹配，才会导入。

它也考虑到了已有文件的实际命名方式：在作品、季度和集数范围都能确认的前提下，支持识别季度目录中的 `001.mkv`、`002.mkv` 等文件。

扫描与复核阶段只读取网盘文件、更新媒体库数据库，不重命名、移动或删除原文件。复核完成后，确认缺少的已播集会自动排队补集；遇到无法识别的视频、季度冲突或元数据异常，则会列入待核对报告，暂缓自动补集。

对于长期维护媒体库的人来说，这能减少重新建库的工作量。不过，网盘同步只能恢复能够从文件中确认的信息，旧任务历史和用户设置仍需要依靠数据库备份。

## 按服务配置代理，更方便排查网络问题

自部署时，不同服务的网络可达性往往不同。可能网盘连接正常，但元数据接口访问不稳定；也可能只有某个资源服务需要代理。

巡影多元数据版支持为 AniList、TMDB、PanSou、assrt.net、Jev 分别选择是否启用 SOCKS5 代理，并提供代理入口和目标连接测试。

这让网络配置更有针对性，也方便定位问题发生在哪个环节。

使用 Docker 时需要留意：容器中的 `127.0.0.1` 指向容器自身。代理地址应填写容器实际能够访问的主机或局域网地址。

## 支持哪些网盘和服务？

当前项目支持以下网盘及获取方式：

| 网盘 | 获取方式 |
| --- | --- |
| 夸克 | 分享链转存 |
| 115 | 分享链与磁力 |
| 123 网盘 | 分享链与磁力 |
| 光鸭云盘 | 分享链与磁力 |
| 天翼云盘 | 分享链转存 |

资源和模型方面，可以配置 OpenAI 兼容模型、PanSou、可选的 Prowlarr，以及字幕来源和 Jev 候选预筛。

未配置自有模型时，应用默认使用 Kilo Code 公共免费模型池。任务中的查询、留言、候选结果和文件名等上下文会发送给 Kilo 及其上游模型提供商，使用前可以根据自己的需要，改为指定的 OpenAI 兼容服务。

## 如何部署？

主机需要提前安装 Git、Docker Engine 和 Docker Compose v2。在终端执行：

```bash
git clone https://github.com/QFgood/mediary-scout-o0521.git
cd mediary-scout-o0521
GIT_SHA="$(git rev-parse HEAD)" docker compose up -d --build
```

首次启动需要拉取依赖镜像并构建 Web 镜像。完成后，通过浏览器访问：

```text
http://<主机IP>:3000
```

Compose 会启动 Web、后台 Worker、PostgreSQL、PanSou 和更新辅助服务。

接下来，在「设置 → 网盘」绑定网盘，再到「设置 → 资源与服务」检查模型、元数据和资源搜索配置。AniList 公共 API 默认不需要 Key；有网络访问需求时，再配置对应服务的 SOCKS5 代理。

完成这些设置后，就可以搜索作品并点击「获取」，也可以先通过「同步网盘资源」恢复已有媒体库。

日常更新前建议先备份数据库。项目提供了备份脚本：

```bash
./scripts/pg-backup.sh ./backups
```

PostgreSQL 数据保存在 `pgdata` 卷中，更新时应保留数据卷；`docker compose down -v` 会删除卷，操作前需要特别留意。

## 适合谁使用？

如果你已经使用网盘保存影视资源，希望集中管理电影、剧集和动漫，或者正在寻找能够部署到 NAS 上的追更工具，巡影多元数据版值得了解。

它尤其适合有动漫追踪需求、需要从已有网盘目录恢复媒体库，以及希望自行配置模型、资源源和网络连接的用户。

从双元数据搜索，到 AniList 原生追更，再到网盘恢复与按服务代理，这个版本关注的是媒体库长期使用中那些具体而琐碎的问题：作品如何识别、更新如何追踪、已有文件如何重新入库，以及服务连接异常时如何排查。

项目沿用 **0BSD 开源许可证**，保留上游版权与许可信息。欢迎查看源码、阅读文档，也欢迎支持这个独立维护的 Docker 多元数据版本。
